# D4SEC.1C.2C.2 enterprise/internal audit reader governance audit

## Verdict

**GO**, without a Prisma migration or seed, for a separate, read-only `GET /platform/audit/events` boundary backed only by `resolvePlatformAuthority(User.id)`. The existing `AuditLog` supports historical actor/facility relations, normalized security evidence in JSON, deterministic keyset pagination, and an access-audit row. D4SEC.1C.3 must later replace or augment this deliberately narrow single-platform-principal bridge with independently governed staff capabilities.

## Repository inventory

1. `AuditLog` has UUID `id`, `createdAt`, nullable immutable `userId` and `facilityId`, nullable patient/encounter/order links, entity/action, request context, and arbitrary JSON `metadata`. Its indexes are exactly `userId`, `facilityId`, `createdAt`, and `encounterId`; no compound search index exists.
2. `AuditService` appends through `auditLog.create`, merges request-context role/source, supports transaction-bound writes, and otherwise applies configurable best-effort/fail-closed behavior. The `security-admin-audit` adapter validates metadata recursively/case-insensitively for secret-like keys and normalizes event, outcome, severity, source operation, denial reason, and evidence.
3. `GET /admin/audit/events` is the only general audit reader. It is a customer/facility reader: active facility plus exact active ADMIN scope, facility predicate adjacent to the query, bounded cursor pagination, filters, platform-actor neutralization, and no raw actor ID in the response. Catalog, billing, encounter timeline and monitoring reads are domain-specific—not an internal/global audit reader. No enterprise/internal audit controller, DTO, web route, or test exists.
4. `resolvePlatformAuthority` is the D4SEC.1A database authority: active User + `canCreateFacilities` + active `MEDORA_SUPER_ADMIN` assignment. Email, headers, frontend state, role string alone and the capability flag alone are insufficient. `RolesGuard` supports role-based facility boundaries but is not adequate for this global reader; authenticated identity must be resolved again by immutable User.id.
5. `ADMIN` means facility administration through an active scoped assignment. `MEDORA_SUPER_ADMIN` is a role code used broadly, but D4SEC.1A makes the string alone non-authoritative for platform operations. Request facility context derives from JWT/cookie/header on customer routes; it must have no bearing on enterprise authority.
6. Customer pagination is newest-first `(createdAt,id)` keyset order, default 50/max 200, with an opaque but unsigned cursor. Customer filters include date range, actor, encounter, entity, action and presets. Unknown controls are rejected by strict Zod parsing.
7. Metadata is heterogeneous and sometimes contains encounter/order/patient identifiers, operational values, free text, audit actor snapshots and normalized security-admin fields. It may therefore contain PHI or secrets despite many call sites documenting PHI-safe intent. Returning raw metadata is unsafe. A universal PHI classifier is not supportable; enterprise evidence must use a small semantic allowlist and omit unknown/nested/arbitrary metadata fail closed.
8. Audit classifications are primarily `AuditAction`; normalized security events additionally carry `event`, `outcome`, `severity`, and `sourceOperation` in metadata. No normalized schema columns exist for those values.
9. D4SEC.1C.2C.1 changed actor and facility audit FKs to restrictive retention. Inactive Users and Facilities remain related and readable. Null user represents system attribution; null facility represents global/platform scope. Current memberships must not be consulted to interpret historical rows.
10. No governed audit-log export/download/report path exists. Chart, ROI, billing and report exports are separate domain workflows and do not authorize AuditLog export. Enterprise audit export is deferred pending separate `AUDIT_EXPORT` capability, purpose/ticket, bounded sanitized projection, artifact security, download auditing, PHI classification and retention controls.
11. No audit retention executor, legal-hold registry, WORM archive, disposition workflow or audit-specific deletion policy exists. D4SEC.1C.2C.1 removed destructive AuditLog cleanup from the development patient cleanup script and established restrictive attribution. Routine destructive deletion remains prohibited; no `AuditLog.delete/deleteMany` may be introduced.
12. No existing privileged audit-read auditing exists for a global reader because no such reader exists. This slice must append one normalized access event after each successful page and a safe denial event for authenticated, authority-resolved denials; unauthenticated noise remains unaudited.

## Governance disposition

Retention classes requiring future policy include authentication/security administration, platform administration, clinical/chart access, clinical record-change evidence, billing/export/ROI, public-health/compliance, operational events and break-glass. Legal hold must override disposition; archive needs encryption, immutable manifests/digests, retrieval verification and governed access. Automated disposition is deferred until legal durations, archive verification, hold precedence, approvals and an independently privileged executor exist. Backups are not a legal-hold archive.

No schema deficiency blocks the bounded reader. Compound indexes and normalized classification columns may be future performance/governance improvements, but are not required for correctness at current scope. No production operation was performed.
