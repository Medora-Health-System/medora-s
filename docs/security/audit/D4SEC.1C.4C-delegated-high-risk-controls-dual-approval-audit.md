# D4SEC.1C.4C delegated high-risk controls and dual approval — audit

## Verdict
No unresolved P0 ambiguity was found. Runtime schema and code provide reusable immutable `User.id`, D4SEC.1A principal resolution, active/unrevoked grant resolution, session-bound `AuthSession` assurance, append-only grant/lifecycle attribution, transactional `AuditLog`, strict Zod DTOs, and partial uniqueness for active grants. The missing authority was a narrow approval capability and immutable request/state record.

## Runtime findings
The catalog contains 24 definitions. **CRITICAL:** `FACILITY_CREATE`, `FACILITY_ACTIVATE`, `STAFF_PROVISION`, `STAFF_GRANT_CAPABILITIES`, `STAFF_REVOKE_CAPABILITIES`, `SECURITY_MFA_RECOVERY`, `SECURITY_PRIVILEGED_ACTIONS`, `COMPLIANCE_CONTROLS_MANAGE`, `BILLING_RCM_MANAGE`, `AUDIT_EXPORT`. **HIGH:** `FACILITY_CONFIGURE`, `STAFF_VIEW`, `SECURITY_ACCESS_VIEW`, `SECURITY_AUDIT_VIEW`, `COMPLIANCE_AUDIT_VIEW`, `COMPLIANCE_ROI_MONITOR`, `COMPLIANCE_EXPORT_MONITOR`, `BILLING_RCM_VIEW`, `CATALOG_CONFIG_MANAGE`, `SYSTEM_BACKUP_READINESS_VIEW`, `SYSTEM_GOLIVE_MONITOR`. Remaining catalog entries are MODERATE; none are LOW.

D4SEC.1C.4B kept classification, provision, activation, deactivation, persona changes, grants and revocations principal-only in both controller and service. Reads already support delegated `STAFF_VIEW`. Only staff provision and manual capability grant have safe, implemented execution adapters suitable for dual control now. Direct provision/grant remain principal-only bootstrap paths, explicitly preventing a delegated bypass. Revocation and deactivation reduce authority and should execute immediately for `STAFF_REVOKE_CAPABILITIES` and `STAFF_PROVISION`, respectively, with recent MFA. Activation, classification, and persona changes remain principal-only; persona reconciliation cannot auto-grant CRITICAL definitions.

## Gap and threat analysis
A request previously had no immutable scope, independent approver, expiry, state machine, replay claim, or execution-time authority/state revalidation. Request IDs must never be bearer authority. Main threats are concurrent execution, stale requester/approver grants or sessions, target/capability changes, altered JSON scope, requester self-approval, target approval, self-grant, persona bypass, and audit/mutation partial failure. A SHA-256 digest over a canonical server-built operation/target/parameter object addresses substitution. Conditional status updates in the same database transaction as mutation/history/audit address replay and races. A 15-minute server-calculated TTL limits stale approvals. Both stored session IDs are independently re-read at execution.

## Target policy
`PRIVILEGED_ACTION_APPROVE` is a dedicated CRITICAL definition. It is not part of any persona, is not granted or seeded, and can be assigned only through the same governed critical grant flow or D4SEC.1A bootstrap. `STAFF_GRANT_CAPABILITIES` is not universal approval authority. Requester and target cannot approve. Principal retains bootstrap/emergency override but does not turn role strings, email, facility membership, or `canCreateFacilities` alone into authority.

Risk policy: MODERATE = explicit active grant/authenticated session/audit when sensitive; HIGH = the same plus recent session-bound MFA; CRITICAL = the same plus dual control only for operations marked dual-controlled. Capability risk and operation policy are server-derived. Current dual adapters: `STAFF_PROVISION` and `STAFF_GRANT_CAPABILITY`. Future candidate policies are deferred until their runtime mutation adapters exist.

## Transaction and audit requirements
Execution conditionally claims `APPROVED`, revalidates digest, expiry, requester/approver active authority and their exact fresh sessions, target and capability state, performs one bounded mutation, writes grant/lifecycle provenance and required audit, and finalizes `EXECUTED` in one transaction. Failure rolls back elevation; a safe failure audit is attempted outside the rolled-back transaction. Events are REQUESTED, APPROVED, REJECTED, CANCELLED, EXPIRED, EXECUTED, EXECUTION_FAILED, DENIED plus existing grant/revoke/lifecycle events. Metadata is identifier-only and passes the existing secret-key rejection policy; no PHI or credentials are accepted by DTOs.

## Residual/deferrals
PostgreSQL-backed concurrency and full-chain migration E2E remain a pre-production gate if a disposable database is unavailable. Generic future facility, billing, compliance, audit export, and MFA recovery execution is deliberately absent. Request failure audit and protected mutation cannot be atomic together when the mutation transaction rolls back; the mutation remains fail-closed. Operational governance must determine humans eligible to receive approval authority.
