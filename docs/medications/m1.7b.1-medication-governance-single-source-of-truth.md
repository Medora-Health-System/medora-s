# M1.7B.1 — Medication Governance Single Source of Truth

## Part 1 — Architecture design

### Problem

Orders enrichment, MAR UI, client pre-POST validation, and `MedicationAdministrationService.create()` each derived governance independently — causing hidden panels, POST 400s, and policy drift (especially Hydromorphone double-check / pharmacy / LASA).

### Solution

One pure resolver in `@medora/shared`:

```
resolveMedicationAdministrationRequirements(input)
```

**Inputs (serializable):**

| Slice | Source |
|-------|--------|
| `catalog` | `catalogMedication` row |
| `product` | `medicationProduct.concept.safetyProfile` + `administrationProfile` |
| `pharmacy` | Latest `pharmacyVerification` row (optional) |
| `marContext` | `marAction`, `route`, `isContinuousInfusion` |

**Outputs:**

| Field | Purpose |
|-------|---------|
| `snapshot` | Order item `medicationSafetyGovernance` (display + API) |
| `resolveInput` | Client re-resolve with updated route/infusion |
| `display.badges` / `display.summaryLines` | MAR badges and summary |
| `workflows.*` | Per-domain applies, workflowVisible, validator contexts |
| `blockingWorkflowVisible` | Modal blocking sections gate |
| `validateMedicationAdministrationGovernance()` | Client + server validation |

**Policy (M1.7A.9)** applied inside resolver only:

- Double-check: insulin, anticoagulant, blood products, PCA/PCP opioid, continuous-infusion opioid
- Pharmacy: informational at MAR; never blocks administration

### Data flow

```
catalog + product + pharmacy + marContext
        ↓
mergeMedicationGovernanceIdentity()   ← packages/shared/medicationGovernanceMerge.ts
        ↓
resolveMedicationAdministrationRequirements()
        ↓
┌───────────────┬────────────────┬──────────────────┐
│ Orders API    │ MAR UI         │ MAR POST API     │
│ attach snapshot│ requirements  │ validate + persist│
└───────────────┴────────────────┴──────────────────┘
```

### Consumers

1. **Orders enrichment** — `attachMedicationSafetyGovernanceToOrderItem` + `medicationGovernanceResolveInput`
2. **MAR display** — `requirements.display.displayInput` for badges/summary
3. **MAR modal workflow** — `requirements.workflows.*.workflowVisible` (no local `mar*WorkflowVisible` logic)
4. **Client validation** — `validateMedicationAdministrationGovernance`
5. **API validation** — same function in `MedicationAdministrationService.create()`

## Part 5 — Hydromorphone MAR validation proof

**Fixture:** `HYDROMORPHONE_2MG_ML_INJECTABLE`, Schedule II, `HIGH_ALERT_OPIOID`, LASA HIGH, pharmacy PENDING, route IV, not continuous infusion.

**Resolver output:**

- `workflows.highAlert.workflowVisible` = **false**
- `workflows.pharmacy.workflowVisible` = **false**
- `workflows.lasa.workflowVisible` = **true**
- `snapshot.requiresDoubleSign` = **false**

**Validation:**

- Without LASA ack → `LASA_ACKNOWLEDGEMENT_REQUIRED`
- With LASA ack + selection confirmed → **ok** (no pharmacy override, no double-check verifier)

**API proof:** `medication-administration-hydromorphone.spec.ts` — `create()` succeeds with pharmacy PENDING and LASA ack only.
